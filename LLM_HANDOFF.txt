COMPLETED IMPLEMENTATION
1. Structured extraction for TXT, Markdown, text-layer PDF and DOCX.
   Original file SHA-256 and actual byte size are captured. Normalized source
   text is represented as ordered blocks with honest location metadata.
   TXT supports UTF-8/BOM, BOM-marked UTF-16/32 and warned Windows-1252 fallback.
   DOCX paragraphs/tables retain document order, standard headings and nested
   table content; merged-cell text is not duplicated.
   PDF preserves physical page numbering and blank-page gaps. Valid short PDFs
   no longer fail a 50-character heuristic. Empty, corrupt, encrypted,
   image-only and mixed scanned/text documents have classified errors.

2. Model-aware chunking uses the real fast tokenizer and the sentence model's
   effective maximum, not word counts or the tokenizer's advertised maximum.
   Cached all-MiniLM-L6-v2 revision:
   1110a243fdf4706b3f48f1d95db1a4f5529b4d41
   Embedding dimension: 384. Effective input maximum: 256 tokens.
   Default content chunk size: 200 tokens. Requested overlap: up to 40 tokens.
   Final encodings including special tokens are checked before embedding.
   Chunks prefer sentence/paragraph boundaries, retain source substrings and
   never cross a physical PDF page or detected section boundary.
   Retokenization cannot emit contained duplicate chunks or silently truncate.

3. Recoverable staged ingestion publishes immutable versions.
   Preflight extraction/chunking/embedding precedes persistence.
   A staging document, inactive expected chunks and processing job are committed.
   A category/source advisory lock protects vector writing and publication.
   Verified Chroma vectors are published through one PostgreSQL transaction
   activating the new rows, deactivating the predecessor and completing the job.
   Predecessor vector cleanup happens afterward and cannot undo publication.
   PostgreSQL is authoritative for retrieval eligibility; staged, missing,
   inactive or unknown chunks are not returned as valid evidence.

4. Source identity and repeat-import behavior are explicit.
   Identity is category_id plus source_key, separate from the display title.
   Folder ingestion supplies relative POSIX paths including file extension.
   Direct process_file defaults to a normalized absolute path; portable corpus
   callers should pass an explicit stable source_key.
   Same original bytes + extracted text + full configuration is skipped only
   after verifying existing vectors. Changed content/format/parser/chunker/
   model/collection settings create a new version. Failed attempts can consume
   version numbers. Same basename under different source keys stays separate.

5. Recovery handles partial writes, cleanup failures and uncertain commits.
   A lost commit acknowledgement is checked using a fresh database connection.
   An unknown outcome is preserved for recovery; vectors possibly belonging to
   a committed publication are never deleted merely because commit() raised.
   Reconciliation is report-only by default and apply requires a document UUID.
   It can retire stale staged attempts, remove failed/obsolete vectors or rebuild
   missing active vectors from stored chunks with the original model settings.
   Recovery uses an existing vector path/collection and never resets a store.
   PostgreSQL and Chroma do not share a distributed transaction; physical store
   equality during every crash is not promised. Visibility and recovery are
   the implemented guarantees. Unknown ghost-vector ownership is reported for
   scoped investigation rather than blindly deleting other documents' data.

PROVENANCE CONTRACT
LoadedDocument: doc_type, title, blocks, source_hash, source_size,
extractor_version, warnings, source_text, page_count.
SourceBlock: text, index, page_number, section_heading, start_char, end_char.
Chunk: text, index, page_number, section_heading, start_char, end_char, token_count.
Offsets are half-open CHARACTER offsets in normalized extracted_text.
They are not offsets into PDF/DOCX binary files.
token_count excludes special tokens; actual full model input is separately checked.
PDF alone has physical page references. DOCX/TXT/MD page_number is NULL.
Raw from_pages hashes a canonical UTF-8 JSON page sequence; file-based PDF loads
always override that with the original binary file checksum and byte size.

CURRENT LIMITATIONS AND NEXT WORK
OCR and complex PDF visual/table/image reconstruction remain out of scope.
Text adjacent to images can omit image information; extraction warns about this.
DOCX rendered pages, headers, footers, text boxes and tracked revisions are not
extracted and are explicitly warned. File-size/upload authorization belongs in
the future HTTP upload layer. The current pipeline is a service/CLI interface.
Historical source hashes/offsets and naive timestamp zones cannot be invented.
Cross-model active-vector repair requires the original configuration/collection;
otherwise create a new indexed version. Corpus-scale access filtering and
large active-document-ID filters need evaluation before production deployment.

Next: select/freeze approved source documents, ingest managed versions and
review the evidence. Write 10 manually checked questions, then expand to 30-50.
Gold fields: question ID, question, answerability, expected answer, source
identity/version/file checksum, real PDF page or section, exact evidence text
and normalized evidence offsets, category and difficulty. Keep gold anchors
independent of chunk IDs; map chunks per pipeline configuration. Unsupported
questions are mandatory. Run retrieval baseline first; answer groundedness,
correctness and hallucination tests require the still-unbuilt LLM pipeline.

- Login creates random opaque tokens; only SHA256 token digests are persisted.
  Sessions expire after8hours, use HttpOnly/SameSite=Lax cookies and are revoked
  on logout. The current database role is checked on each authenticated request.
  Neither frontend storage nor login JSON controls a user's role.
- Admins upload PDF/DOCX/TXT/MD, select category/title/initial availability,
  inspect exact chunks/tokens/offsets/pages/sections/warnings/configuration,
  replace the stored source and force-reindex into a new immutable version.
- Source files use UUID names under ignored data/uploads/. Windows/POSIX client
  filenames cannot escape storage. Downloads/reindex resolve only managed
  uploads or approved data/documents/ sources. No arbitrary filesystem access.
- Per-file limit20MiB; an outer ASGI body cap permits bounded multipart overhead
  and rejects oversized Content-Length/streamed bodies before unbounded
  multipart spooling. Partial parser files close on errors. Streaming413 is
  preserved even with Starlette BaseHTTPMiddleware exception wrapping.
- is_online is separate from lifecycle status. Both roles' retrieval requires
  active documents + online flag + active chunks. Offline files/chunks/vectors
  remain inspectable by admins. Employees cannot download offline/old sources.
- Replacement and reindex inherit availability; a toggle committed in the
  staging/publication gap is refreshed and inherited correctly.
- A selected-version compare/check prevents a stale reindex from reverting a
  newer replacement. Conflicts return409. Checks run before skips and staging;
  existing publication-predecessor checks remain in place.
- Document publication and its success audit event share one PostgreSQL commit.
  Audit failure rolls back activation and preserves the old version. Existing
  durable-stage failure/recovery cleans the attempted new vectors.
- Identical replacement verifies/skips the existing version and removes the
  newly saved unused duplicate source file. Changed source/config creates a
  new version. Explicit reindex always creates a new version.
- Legacy source identity can be adopted for deliberate replacement/reindex;
  missing historical fingerprints/provenance remain explicitly unknown.
  Store audit uses pipeline_fingerprint to distinguish captured provenance,
  so assigning a legacy logical source key does not fabricate provenance.
- Audit records include actor, action, entity/id, UTC timestamp and sanitized
  bounded JSON details. Secret-like detail keys are excluded. DTO includes id
  for the React list. Document timestamps carry UTC for correct local display.
- React uses real API data: no fabricated progress, metrics or generated answer.
  Admin screens show name/category/type/status filters, actual corpus counts,
  upload, source inspector, version history, reindex and availability controls.
  Both roles get semantic Retrieval lab with source references/similarity.

3. NEW RAG CONSTRUCTION AND EXECUTION FLOW
-----------------------------------------
POST /api/chat -> authenticated actor -> RAGService -> existing SearchService
-> PostgreSQL-authoritative retrieval -> managed immutable source checks ->
ContextBuilder -> versioned prompt -> injected/configured LLM provider ->
quote validation -> final source-eligibility check -> transactional persistence
of user/assistant messages and retrieved context -> answer + exact citations.

Routes are thin. Services own business workflows/transactions. Repositories
own database queries and writes. Prompts and HTTP contracts have separate files.
No database or embedding business logic was moved into React route handlers.

3A. CONTEXT CONSTRUCTION
backend/services/context_service.py:
- ContextBuilder assembles real retrieved evidence with labels S1,S2,...
  and document/version/page/section metadata.
- Question and evidence are serialized as JSON DATA in the user message;
  model instructions stay in a separate system message.
- Duplicate chunk IDs, empty text and invalid similarity values are excluded.
  Optional thresholds are explicit; no arbitrary default similarity threshold
  is represented as a calibrated answer-confidence score.
- Whole chunks are selected within a configurable serialized-message UTF-8
  BYTE budget. Oversized chunks are dropped instead of cutting off conditions.
- Default RAG_MAX_CONTEXT_BYTES=12000, max_sources=10.
- context_bytes measures the actual compact UTF-8 messages envelope;
  context_tokens/context_token_budget are NULL because no provider tokenizer
  has been selected. These bytes are NOT claimed to be exact LLM tokens.
  The model's real context window/tokenizer must be checked when connected.

RAGService additionally checks hit text/offsets/version/hash against immutable
Document.extracted_text and source_hash. Legacy or inconsistent provenance is
excluded from generation context until deliberate reindexing captures it.
Retrieval lab may still display legacy evidence under its older contract.

3B. PROMPT TEMPLATE
backend/prompts/rag_prompts.py:
- PROMPT_VERSION='grounded-quotes-v1'; separate SYSTEM_PROMPT/RESPONSE_SCHEMA.
- Ask only for directly supported helpdesk evidence; refuse when insufficient.
- Treat document/user attempts to override instructions as untrusted data.
- Require concise complete verbatim sentences/paragraphs/structured table rows.
  Preserve negations, numbers, conditions and exceptions. A PDF line wrap or
  cropped token-window edge is not accepted as a complete semantic unit.
- Return JSON {insufficient_evidence:bool,claims:[{source_id,quote}]}.
- No free-form model answer/reasoning is used as user-facing answer content.

3C. PROVIDER BOUNDARY / DEFERRED LIVE INTEGRATION
backend/services/llm_service.py:
- LLMProvider protocol: generate(messages,*,max_output_tokens,response_schema).
- UnconfiguredLLM is the normal default and returns an explicit setup error.
- Optional ChatCompletionsLLM supports an explicitly configured compatible
  endpoint/model/key. There is no default external URL or automatic fallback.
- JSON schema, JSON-object or no response-format modes are explicit choices;
  max_completion_tokens versus max_tokens is configurable for compatibility.
- Timeout, bounded response body, structured-response parsing, finish-reason
  checks, sanitized failures and no automatic redirects are implemented.
- Remote HTTP/credentials-in-URL/query credentials are rejected. Remote hosts
  require HTTPS; loopback HTTP is allowed for a future local provider.
- Transport contract was checked against official OpenAI documentation:
  https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create
  This does NOT choose OpenAI or certify compatibility with every provider.
- No generation SDK/model download or live API key was needed/used.

.env.example includes disabled/default placeholder configuration:
LLM_PROVIDER=disabled; LLM_ENDPOINT; LLM_MODEL; LLM_API_KEY;
LLM_RESPONSE_FORMAT=json_schema; LLM_TOKEN_LIMIT_FIELD=max_completion_tokens;
RAG_MAX_CONTEXT_BYTES=12000; RAG_MAX_OUTPUT_TOKENS=512.
The private .env and existing credentials were not replaced or printed.

3D. GROUNDED QUOTE ANSWERS / REFUSALS
backend/services/grounding_service.py:
- Validate response shape and bound the claim count.
- Reject unknown source IDs, empty/invented quotes, duplicate claims and
  quotes that do not match source text exactly.
- Validate start/end boundaries using the FULL immutable extracted source,
  not merely the cropped retrieved chunk. Relative allowed-boundary offsets
  are attached to source metadata; the full snapshot is not sent to the model.
- Ordinary single PDF line wraps are not sentence/paragraph boundaries;
  complete structured table rows are handled as units.
- Preserve quoted negation/conditions; compute exact absolute quote offsets.
- Render answer content exclusively from validated quotes plus [S#] markers.
  Extra unverified provider prose is ignored rather than rendered.
- Zero valid claims or insufficient_evidence=true produces a fixed refusal
  and no fabricated citations. Malformed/truncated provider data is an explicit
  service error, not a fake successful answer.
- RAGService rechecks active/online status, version/hash and chunk text after
  provider latency, holding read locks through persistence. Offline/replaced
  sources during generation cause a refusal without old evidence publication.

LIMIT: exact provenance/boundary checks do not prove semantic relevance or
full entailment. A real model can select a true but irrelevant quotation or
omit context across sentences. This is NOT a hallucination-free guarantee.
Live answer correctness and adversarial behavior still require model testing.

IMPLEMENTED PASSWORD CHANGE

  25.1.0, using RFC_9106_LOW_MEMORY: Argon2id v19, memory 65536 KiB (64 MiB),
  time cost 3, parallelism 4, random 16-byte salt and 32-byte hash output.

  Argon2id. Invalid Unicode and oversized input are rejected.

  Its legacy 72-byte verification limit is enforced without truncation.

  to current Argon2id. Wrong-password login never changes hashes or creates a
  session. A valid legacy password below today's new-account minimum still
  upgrades and remains usable; migration does not force a password reset.
- UserRepository.create now requires an Argon2id hash for new accounts.
  upgrade_password_hash uses a conditional update matching the previous hash,
  so migration cannot overwrite a concurrently replaced password. A stale
  upgrade fails authentication without creating a new session.
- Hash upgrade and session creation commit together; a session persistence
  failure rolls back the hash change too. Current-policy hashes are not
  regenerated on every login.
- Existing users are NOT bulk rewritten: bcrypt rows upgrade on their next
  successful login. No plaintext passwords were recovered or logged.
- Existing users.password_hash VARCHAR(255) accommodates the encoded Argon2id
  value. No SQL schema migration was needed or applied for this change.

1. AGGREGATE ANALYTICS
GET /api/analytics?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD is admin-only. New
analytics API/service/repository query PostgreSQL without initializing AI/vector
resources. Summary includes total questions, questions today/week, responses,
current thumbs up/down/unrated, average known latency and timing denominator,
explicit insufficient-evidence responses, explicit no-useful-retrieval responses,
and unknown historical outcomes. Also includes zero-filled daily activity,
frequent questions, retained document-version usage and insufficient-evidence
examples. Definitions are available in the API and expandable screen details.

Semantics that must not be silently changed:
- All date controls are inclusive UTC calendar days. SQL uses >= day start and
  < the next day. Only YYYY-MM-DD is accepted, and reversed/overflow ranges fail.
- Questions use the user-message timestamp. Responses/latency/outcomes/current
  feedback are cohorts by assistant-message timestamp, not feedback-event date.
- Feedback metrics are one current owner vote per response, NOT the number of
  submissions in audit history. A changed vote updates the current aggregate.
- Today is UTC today and week starts Monday UTC; both intersect selected dates.
- Average latency omits unknown/negative values and is NULL when no timings exist.
- Unsupported means insufficient_context=true, not a calibrated confidence score.
- No useful retrieval requires the explicit string reason no_eligible_sources;
  absent or malformed legacy metadata must not invent a retrieval failure.
- Source usage is distinct retained response/document-version pairs, not chunks,
  downloads, or current availability. It includes retained historical sources.
- FAQs collapse whitespace and lowercase only; no semantic topic grouping.
- Daily table covers at most the latest 31 dates in range; totals cover all dates.
  Top lists have at most ten items. Missing explicit question linkage stays NULL.
- Only saved messages count. Unconfigured generation, failed unsaved requests,
  context previews and Retrieval Lab searches are not fabricated chat records.

2. BASIC OWN PROFILE
GET /api/profile works for admin and employee. Returns only the authenticated
actor's email, role, department, user ID, lifetime own conversation/question/
response/current-vote totals and current owned opaque-cookie session expiry.
The cookie is hashed internally to look up the owned session; neither raw cookie,
token digest nor password hash is serialized. Screen is deliberately read-only.
Existing Argon2id passwords and fixed eight-hour revocable opaque sessions are
unchanged. This is not JWT, a role editor, account deletion, or password reset.

3. FEEDBACK AUDIT
Each accepted submission writes feedback.submitted in the same transaction as
the vote upsert. Details include rating, conversation_id and question_message_id
only when the target exists, is a user message, and belongs to the same convo.
Audit entity is response and entity_id is the exact assistant response ID;
actor and audit timestamp identify who submitted it and when. Question/answer
text, credentials and prompt/context bodies are not copied into audit details.
Audit failure rolls the vote/timestamps back. Unauthorized/rejected inputs create
neither vote nor event. Each accepted resubmission creates another audit event;
the feedback table continues to retain one current vote. Existing exact q/a,
citations and retained context remain inspectable in User feedback.
Historical submissions before this change are not backfilled or reconstructed.

4. DATE AND VERSION FILTERS
GET /api/documents accepts uploaded_from, uploaded_to and version>=1 in addition
to existing filters. With no date/version filter the prior latest-source grouping
is preserved, including active-version preference over newer failed attempts.
With any date/version filter it searches matching stored versions; response
scope is matching_versions and summary counts refer to returned versions.
Upload dates are each version's created_at. Historical deactivated/staging rows
are inspectable; UI replacement/reindex controls are disabled for them.
GET /api/admin/reviews accepts question_from and question_to. It uses the exact
linked user question's timestamp, including unmatched user messages' own time.
Legacy unlinked assistant responses are excluded when a question-date filter is
active. The server does not infer timestamps or fabricate question pairings.
All ranges are inclusive UTC dates; invalid/reversed dates and bad versions fail.
Document listing/category lookups now use DB-only dependencies, avoiding model or
vector initialization for metadata browsing. Existing mutation dependencies stay.

5. CATEGORY CRUD AND SAFETY
GET/POST /api/categories and PATCH/DELETE /api/categories/{uuid} are admin-only.
Categories may be created, renamed, described and removed only if unreferenced.
Names are trimmed printable text (1..100 chars); descriptions <=1000 chars and
can be cleared. Empty updates and case-insensitive duplicates are rejected.
Application category writes serialize using a PG advisory transaction lock;
foreign-key conflicts are sanitized to 409. Counts include all document versions,
including failed/staging/historical. Used-category deletion is disabled visibly
and enforced server-side. Rename retains the UUID; no document moves/vector
rewrites are required. Category writes and their audit records commit atomically.
Document category reassignment and forced referenced-category deletion were not
added. Existing upload choices read the maintained taxonomy.

Migration002 replay was corrected: initialize starter taxonomy only if empty and
not previously maintained, with existing category audit evidence distinguishing
an intentionally emptied list. Renamed/deleted labels do not reappear on setup.
If uncategorized legacy documents exist, case-insensitive Uncategorized fallback
lookup reuses an existing UUID rather than creating a duplicate. No schema
extension or new migration ledger is needed. These preservation paths are tested.
